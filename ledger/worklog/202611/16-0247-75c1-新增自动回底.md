## Process

**技术前提（实读证据）**：

- Skyline 不支持页面全局滚动，页面须配 `disableScroll`，滚动交给自己放的 `scroll-view`：`docs/dependencies/skyline-rendering.md:10`。
- 演示站的实际形态：`demo/src/components/DemoShell.tsx:1` 引入 `ScrollView`，`:34` 是 `<ScrollView scrollY type="custom" className="demo-shell__body">`——库内的滚动来源就是这个节点，不是页面。
- 现有库内唯一用到 ScrollView 的地方是 `src/ui/form/segmented/Segmented.tsx:170`（横向），没有可复用的纵向滚动能力。

**风险点（本单最大不确定项）**：

- `scroll-top` 是受控属性，回顶后再滚下去、再点一次，若赋值与上次相同可能不触发滚动。若实测确实不触发，两条退路：回顶前先置 0 再置目标值，或把 `scrollTop` 控制权完全交给消费方，库只发 `onBackToTop` 回调。
- 受控方案会让可移植性下降（每个消费方都要自己接 onScroll）。这是有意的取舍：库不接管容器，避免和消费方布局打架；若将来第二个项目也要，再考虑提供现成的滚动页容器。

**方案拍板（2026-11-20）**：用户先问「内置固定按钮 vs 消费方自己加」，又质疑成熟库是不是拆的。实查 Ant Design 源码 `components/float-button/BackTop.tsx`：`FloatButton.BackTop` 是独立配套子组件，内部 `useScroll({ getTarget, visibilityHeight })` 算显隐（默认 400），点击 `scrollTo(0, { getContainer, duration })`（默认 450），复用 FloatButton 本体、非受控受控分离。结论照搬其「独立配套 + 复用壳 + 阈值/时长两轴」的形态，但按 Skyline 现实改两处：滚动值外部喂（拿不到 DOM）、回顶逐帧交回消费方（不能库直接 scrollTo）。落码 `src/ui/layout/floating-action/BackToTop.tsx`，导出接组件级与 layout 子域两个 barrel；demo 把回顶挂进同一个 FloatingActionGroup，加阈值/时长两档配置与 40 行滚动占位。

**「同值不触发」风险的设计规避（已废弃，见下）**：逐帧缓动每帧目标值随进度变化，最后一帧显式写 0，不依赖「设同一个值」触发。

**返工——旧方案是错的（2026-11-20，用户真机发现卡顿/残影）**：第一版的 `BackToTop` 接 `scrollTop` + `onScrollTopChange`，逐帧回调驱动回顶。消费方为了喂它只能把滚动位置做成受控 state（`scrollTop={top}` + `onScroll` 回写），形成反馈环：每帧 setState → 整页 setData（单次 8~15ms，超 16ms 丢帧）→ 受控属性把视图往回钉 → 再触发 onScroll。用户症状「快速滚动反复冒出、滚到底反而没了、手动滚也残影」全部由此而来。根因不是阈值算法、不是动画时长，是**在 onScroll 里把滚动位置回写成受控属性**——这是任何小程序教程都会明令禁止的写法。旧 API 本身在诱导错误写法，整体废弃。

**正确写法（按官方文档 + 成熟库逻辑重写）**：
- 微信 scroll-view 官方文档：`scroll-top` 是命令滚动的输入、`onScroll` 是读滚动的输出，二者不该每帧互写；增强模式 `ScrollViewContext.scrollTo({top, duration})` 才是程序化滚动的推荐方式。Taro 文档与本地 `@tarojs/components` 类型确认 `enhanced` 属性存在、`scrollTo` 支持 duration，项目内 `Segmented.tsx:102` 已有 `createSelectorQuery().node()` 同类用法。
- 库侧：`BackToTop` 退成 `FloatingAction` 的外观特化（默认回顶图标），只接离散 `visible` + `onClick`；新增 `useBackToTop` 钩子，滚动位置存 ref、只在阈值布尔翻转时 setState 一次；库不 import Taro、不做动画、不查节点。
- 消费方（demo）：`ScrollView` 不传 `scrollTop`（非受控）、开 `enhanced`、`onScroll` 只读地把 `e.detail.scrollTop` 喂给钩子；回顶一次 `createSelectorQuery().select('#id').node().exec(res => res[0].node.scrollTo({top:0, duration}))`，动画交给视图层。
- DemoShell 的滚动区本身就是回顶目标（传 `scrollViewId`），不再嵌第二层 ScrollView；去掉 `scrollTop` 受控属性与 `onScrollTopChange` 回写。
- 全仓扫描：只有回顶这一条链有此病；`Segmented` 的 `scrollIntoView` 是一次性定位、其余 ScrollView 是纯内容滚动无 onScroll，均不动。

**再返工——两个配置改了没反应（2026-11-20，用户真机反馈）**：用户确认动画/残影已修好，但「回顶阈值」「回顶动画」两档切换无任何变化。查实两个独立根因：
1. 阈值：`useBackToTop` 只在 `onScroll` 回调里算阈值，改阈值（Segmented 点击）不触发 onScroll，`visible` 不重算，要等下一次滚动才生效 → 看起来没用。修法：`lastTop` ref 记住最后滚动位置，`useEffect([visibilityHeight])` 用它在阈值变化时立即重算。
2. 动画：`ScrollViewContext.scrollTo` 的 `duration` **仅在 iOS 下生效**；微信官方公告 2022-12-01 起安卓 WebView 已废弃 duration/velocity，本地 Taro 类型注释同写「仅在 iOS 下生效」→ 0/450/900 三档在安卓与开发者工具观感一致。修法：新增 `useBackTopScroll`，JS 侧 `setTimeout` 逐帧（16ms、ease-out-cubic）算 `driveTop`，时长由 JS 控制、跨端可靠；消费方把 driveTop 绑到 scroll-view 的 scrollTop，**动画期屏蔽 onScroll**（否则退回每帧回写反馈环），结束置回 undefined 恢复非受控并回喂一次位置。此前的一次节点 scrollTo 路线整体废弃。

三块职责定稿：`BackToTop`（外观特化）+ `useBackToTop`（阈值）+ `useBackTopScroll`（时长）。库仍不 import Taro、不查节点。文档写清两条铁律与两版旧 API 废弃原因。

**三返工——回顶过山车（2026-11-20，用户真机反馈「回到顶部马上又回下面又回顶部」）**：上一版 `useBackTopScroll` 逐帧 setState 把 `driveTop` 绑到 scroll-view 的 `scrollTop`，动画结束 `setDriveTop(undefined)` 从受控切回非受控时，视图层弹回它内部记录的旧位置 → 回顶后弹下去、再点又回顶，循环。这正是上轮已标注「未真机验证」的留坑爆了。定为铁律：**绝不把滚动位置绑到 scrollTop 属性**。根除方案：`useBackTopScroll` 改为逐帧调用消费方 `ScrollToCaller`（节点 `scrollTo({top, animated:false})`），全程零滚动 state、零 scrollTop 属性；节点只查一次缓存复用；时长仍由 JS 发帧节奏控制（跨端、不依赖被安卓废弃的 duration）。三版旧契约（逐帧受控回写 / 一次 scrollTo+duration / 逐帧 driveTop 绑 scrollTop）全部写进文档废弃原因。

**四返工——回顶来回蹦（2026-11-20，用户真机「来回蹦两次才回到顶部」）**：第三版逐帧发节点 `scrollTo` 命令，每帧一条让视图层不断重启滚动、目标每 16ms 变化追不上，表现为来回蹦。定论：**回顶动画必须交给视图层一次完成，JS 逐帧驱动（无论改 state 还是发命令）在小程序上都不稳定**。这是第三/四版连续翻车的根因。废弃 `useBackTopScroll` 逐帧钩子与 `ScrollToCaller`，改为 `scrollViewToTop(node, duration)` 一次 `scrollTo({top:0, animated:true, duration})`。duration 仅 iOS 生效是微信平台硬限制（安卓 2022-12 起废弃），不再试图用 JS 绕。另修：本轮重写 `src/ui/layout/index.ts` 时误把 Overlay/Popup/ImagePopup/FloatingAction 等原有导出冲掉，导致 9 条无关测试失败；已从 HEAD 恢复原导出再增量追加，test 回到 183/183。

**瞬间档修复（2026-11-20，用户确认过山车已好、要求修剩余的动画缺陷）**：用户真机发现「瞬间」档仍有动效、450/900 无区别。查实两件事：① 瞬间档是我代码 bug——原实现 `animated:true + duration:0`，安卓把 0 当无效值忽略、照播默认动画；修为 `duration<=0` 传 `animated:false`，跨端无动画直接回顶。② 450/900 无区别是微信平台硬限制（duration 仅 iOS 生效、安卓 2022-12 废弃），用户知晓后接受，不再试图 JS 绕过。用户明确「先提交」「把该修的 bug 修了」，本轮修完即提交推送。
