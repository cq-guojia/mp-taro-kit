### 三、成熟方案与平台约束

- 微信官方：`app.json` 的 `usingComponents` 自开发者工具 1.02.1810190 起支持全局组件（https://developers.weixin.qq.com/miniprogram/dev/framework/custom-component/），但全局声明视为**所有页面引用**，即每页实例化——与「单例栈 + 单渲染点」的命令式语义相悖。
- Taro 注入插件：`taro-inject-components`（http://gitgub.com/caidix/taro-inject-components）、`taro-global-component`（https://npm.io/package/taro-global-component）、`taro-plugin-inject-component`（https://npmjs.com/package/taro-plugin-inject-component）**全是 webpack loader**，要求 Taro 3.6+ webpack；本仓 `demo/config/index.js:41` 是 `compiler: 'vite'`，**直接用不了**。要自动注入只能自研 Vite transform 插件（AST/JSX、HMR、Skyline 验证都有代价）。
- 新项目实证：`koc-weapp-zuche/docs/design/external/wechat-custom-tabbar.md:27-32` 记录 Skyline + `lazyCodeLoading: 'requiredComponents'` 下 base.wxml 找不到 utils.wxs、glass-easel 下 externalClasses 类型缺口（`a.indexOf is not a function`）、Skyline 对 inset 简写解析严格——自动注入/全局组件在本仓渲染栈上有真实坑。

### 五、五类专家讨论与收敛

- **架构专家**：选 B。命令式 UI 是应用级横切能力，宿主应在组件树根；A 把 12 个组件下沉页面基座是层次错位；C 在本仓 Vite 下不可用。改判条件：需要页面级隔离、或改 webpack 且强诉求零配置。
- **Taro 专家**：选 B + store/ui。自研 Vite transform 可行但坑多（JSX/TS 形态、HMR、Skyline）；`app.json usingComponents` 只按路径注册原生组件，不会自动包住 Taro/React 页面，对本仓不适用。
- **小程序专家**：选 B。全局 usingComponents 等于每页引用、每页实例化且状态不同步，重演老项目；App 宿主更贴单例栈语义。提醒：App 宿主 fixed 覆盖力在 Skyline 未证实、宿主重建会清 mounted、按需注入 wxs 缺失、glass-easel externalClasses 缺口。真机三验：fixed 跨 tab 覆盖、lazyCodeLoading 下 wxs/分包注入、跨页连触发的排队与路由切换清理。
- **资深程序员**：全局命令不需要基础页继承；若要页面级壳，最小形态是 `createPageBase(config)` / `withPageBase(Comp)` 工厂（库出工厂、项目扩展一次、页面只 `export default createAppPage({...})`），与 OverlayHost 分工：宿主管全局浮层、工厂管页面壳，**页面内勿重挂 OverlayHost**。担心工厂泛型推导退化重蹈 `@ts-ignore`。
- **资深前端专家**：不需「基础页继承」心智模型——模块级命令 API + 入口 configure 一次 + 页面一宿主，业务只 import 不继承。契约应写成「当前应用唯一 `<OverlayHost />`，禁二次宿主，未挂同步抛修复 Error，dev 断言 0 或 1」。避开 eventCenter 静默失效：单例状态 + 宿主订阅、Promise 回调入模块级 Map。若做基础页，只放宿主/主题/错误权限注册，**绝不放命令实现、业务弹窗、show 态判断、私有 store/事件总线**。

**分歧点**：是否需要「基础页」抽象。四位（架构/Taro/小程序/前端）认为命令式 API 不需要它，现有 B 已解决用户痛点；资深程序员提出可做工厂，但明确它是页面级壳、与命令式 API 无关。**收敛**：命令式 API **不做基础页继承**，采用 B；页面级壳（NavBar/主题/安全区）若用户后续要做，另立任务用工厂形态，不塞进本决议。

### 七、补充复核：「一条注入」可行性（用户追问）

- 用户问：能不能库直接帮注入，或打包一个基本包，消费方只挂一条？
- 答案：**做不到零代码，但做得到一条 HOC**。
- 本仓 `demo/src/app.tsx:101-108` 已证明 App 的 children 是所有页面，App 挂一次 `<OverlayHost />` 覆盖全站。
- 可收进一条的四项：`<OverlayHost />`（完全可）、`configureSafeArea`（取值需 Taro peer，放 Taro-aware 出口）、`configure(faces)`（部分：Taro 默认实现可代填，业务 request/login/支付策略仍需传入，`src/core/configure.ts:17-31,46-54`）、`setThemeMode`（部分：需宿主 `theme.json` 配色，`demo/src/app.tsx:68-77,91-99`）。
- 必须留在消费方：`config/index.js` 插件行（`demo/config/index.js:28-29`）、主题样式四选一 import（`demo/src/app.tsx:14`）、`app.json` + `theme.json`（`docs/api/exports.md:176-202`）。
- 最小可行形态：新增 `mp-taro-kit/app` 子出口（package.json:21-74 无此键，需新增；主出口不能静态 import Taro，`src/index.ts:1-5`），API `createKitApp(App, { faces, theme })`，内部做一次性 configure/safeArea/theme + `children + <OverlayHost />`；`configure` 是整体覆盖（`src/core/configure.ts:55-65`），必须加一次性 guard，不能放 render 里。
- 零代码注入不可行：Taro 4 只读配置的 plugins，不扫描 node_modules（`docs/api/config.md:117`）；postinstall 在 pnpm 默认不执行；本仓 Vite 无现成 transform 插件，第三方注入插件全是 webpack loader。

### 八、落码方案（批准版）

用户追问后澄清并完成决策依据，最终方案：

1. **拆三件 host**：`OverlayHost.tsx` 拆成 `ToastHost` / `DialogHost` / `LoadingHost`，各自只 import 自己需要的组件；遮罩 `<Overlay>` 只进 `DialogHost`，Toast/Loading 不碰遮罩。证据：Ant Design Mobile 的 Toast 独立且默认 `mask:false`（https://mobile.ant.design/components/toast）、Dialog 独立、TDesign 小程序同构；本仓 `OverlayHost.tsx:47-51`（toast）与 `:41-45`（loading）本就没遮罩，只有 `:56` dialog 用。
2. **按能力改造 mounted 契约**：`commands.ts:6-12` 的单一 `ensureMounted` 改为按能力判定（toast/dialog/loading 各自 host 挂没挂），`state.ts:24-25` 的单个 `mounted` 布尔改为分能力标记。没挂对应 host 就调对应 API 时同步抛带修复指引。
3. **`mp-taro-kit/app` 新出口 + `createKitApp(App, opts)`**：消费方 app.tsx 一行接入；库内做 configure(faces) + configureSafeArea + setThemeMode + 挂 hosts。`hosts` 默认三件全给，可传数组覆盖实现"用哪个打哪个"。configure 一次性 guard（重复调用是整体覆盖，`src/core/configure.ts:55-65`）。主出口 `src/index.ts:1-5` 不静态 import Taro 的约束不动，Taro-aware 代码只在新出口。零代码注入否决（Vite 无现成插件）。
4. **`KitPage` 公共页面组件**（不是"工厂"新概念，就是每页包一层的公共组件，与成熟项目 BasicLayout/PageContainer 同形态）：每页包一层，默认渲染右侧浮动列（回顶 + 设置），某页 `hideActions` 屏蔽、某页 `actions` 追加。库侧默认回顶项，业务自定义项（含设置面板）从 props 进。不继承、不编译注入。
5. **登录窗注册口**：`setLoginDialog(...)`，业务 app 入口注册一次，库只给协议与调度、UI 归业务。参照 `koc-weapp-zuche/docs/design/permission.md:45-53,66` 注入器模式。
6. **demo 接入**：`demo/src/app.tsx` 换成 `createKitApp(App, {...})`；`DemoShell` 收编浮动列到 `KitPage`（`demo/src/components/DemoShell.tsx:35,56` 的 floating 插槽改造）。
7. **文档**：`docs/api/exports.md:57-59` 口径统一（app 入口挂一次、全站唯一、未挂抛错）；新增 `docs/api/app.md`（createKitApp/三 host/KitPage/注册口）；`docs/README.md` 挂索引；更新 architecture 说明。
8. **门禁 + 专家检查**：build/test/guard/demo build/codelint/docwriter 全过；组织专家检查，有问题就改、改了再查，直到无问题再汇报。
