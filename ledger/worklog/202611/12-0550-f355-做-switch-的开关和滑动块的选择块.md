拍板记录（一条一条过，每条都带「为什么 / 影响」）：

**⑦ 超宽滚动 = 内置 `scrollable`（方案 B）** — 2026-11-12
- 为什么：这是开源 UI 库，不能假设「使用者不会超过十几个频道」，把能力推给宿主等于没做；而且 A 方案限死了体验 —— 宿主外层套 `ScrollView` 只能拿到滚动，拿不到「选中段自动滚进视野」「首尾留白」。
- 影响：组件内多一层 `ScrollView scroll-x`（DOM 与样式各多一层）；`fit` 模式下宽 = 内容总和，超出即横向滚动，切段时组件主动把目标段滚进视野；`fill` 模式不滚动。

**③ Button 补 `size` 三档，且改用固定 height** — 2026-11-12
- 为什么：Button 现在没有 size，40px 是 `padding 8 + --mptk-line-lg 24` 撑出来的（`src/ui/actions/style/index.scss:7-13`），与 Switch / Segmented 的 32 / 40 / 48 固定高不同轴，并排必然不齐。
- 影响：Button 的 `size` 取同一套 `--mptk-control-h-*`，高度写成固定值、不再由 padding 撑；**默认档 `lg`(48)**，与 Switch / Segmented / Input 保持一致（用户明确「48 那一档是肯定要的，要和 input、滑动块一致」）。
- 用户另提「型号是不是太少」：现有三档是 WeUI 官方按钮高度三档，要扩只能往 24（小标签）或 56（Cell 高度档）扩，记在 3b 待评估。

**④ 圆角统一抽象：一套语义变量 + 一个 `radius` 参数** — 2026-11-12
- 为什么：现在每个组件自己写档位（Button `md` 12、Segmented 容器 `md` 12、滑块 `sm` 8），要整体调就得逐个改、必漏；用户要求「抽象出来一个圆角样式，传一个参数就自动切」。
- 做法：三层，组件不写像素 —— ① token `--mptk-radius-*`（已有 4/8/12/16/20/999）；② 语义层 `--mptk-control-radius`（控件默认 `sm` = 8），Button / Segmented 容器 / 滑块 / 将来 Input 全引用它；③ 组件 `radius` 参数（默认档 / `pill` 半圆），只翻成类名或内联变量，改一处全体跟着变。
- 影响：整体降一号（12 → 8，滑块 8 → 4），**范围含 Cell / Dialog / Toast / Popup**（现状 12 / 12 / 16 / 16，2026-11-12 用户拍板「统一都降，先保持一致」；这些容器之后由用户逐个过、逐个别调）。
- 半圆为什么用 `999px` 不用 `50%`：百分比圆角的水平半径按**宽**算、垂直半径按**高**算，`50%` 在 120×48 的按钮上得到 60×24 的椭圆角，整块会变成一个扁椭圆；`999px` 超过短边一半后会被自动钳到「短边的一半」= 24，左右两端才是真正的半圆端帽。正方形上两者等价，按钮是长方形，所以只能用 `999px`（库内 `--mptk-radius-pill`）。

**① 段宽默认 `fit`，比例用 CSS 自动均摊** — 2026-11-12
- 为什么：选择块的宽应该由内容决定（两个字窄、四个字宽，整块 = 各段之和），这是「不占满一行」的直觉形态；`equal`（现状）与 `ratio` 都作为显式模式保留。
- 能不能分清：能。`fit` 下每段宽 = 内容 + 左右内边距，实测能拿到各自 `left/width`，滑块按实测值定位，不存在「分不出来」的问题。
- 比例精度：`ratio` 用 `flex-basis: auto` + `flex-grow: 1`（内容先占宽、剩余均摊），**不引入 `weight`**；宽容器下差异会被稀释，消费端真要严格比例时再逐个加权重，不在首版堆参数。
- 影响：`fit` / `ratio` 都要测量（第 ② 条）；`equal` 保持零测量。

**⑥ loading = 底部呼吸条（唯一形态）** — 2026-11-12
- 为什么：转圈要占位置，插在段内就一定撑宽 / 挤字；把文字换成圈又太怪。用户要求「文字不要变，在下面加一条呼吸灯样子的条」。
- 做法：选中段底部叠一条绝对定位的细条（高 2px），透明度在 `0.2 ↔ 1` 之间循环（呼吸），不动布局、不遮字、不换内容；`thumb` 与 `line` 两种指示器共用这一套（推翻上一轮「覆盖转圈 + 底部条」两套）。
- 影响：① 颜色要分形态 —— `thumb` 形态条压在主色滑块上，取 `--mptk-control-on`（白）；`line` 形态无底色，取 `--mptk-control-active`（主色）。② Segmented 上的 `loadingContent`（自定义转圈节点）随之失去意义，建议删掉该 prop。③ Switch / Button 的 loading 仍是转圈，不受影响。

**⑤ `pill` 半圆参数 Button 与 Segmented 都开** — 2026-11-12
- 为什么：两边共用同一套语义变量，实现成本一样，只开一边反而让「圆角一致」出现例外。
- 影响：`radius` 参数在 Button 与 Segmented 上同名同值域（默认档 / `pill`），Switch 不支持（它按形态固定圆角）。

**② 允许 `createSelectorQuery` 测量段宽** — 2026-11-12
- 为什么：段宽不等时百分比算不出位置（`left = 索引 × 百分比` 只对等分成立），只能读一次渲染后的真实尺寸：`selectAll('.mptk-seg__item').boundingClientRect()` 一次批量拿全部段的 `left/width`。
- 准不准：准。返回的就是渲染后的 CSS 像素，已含 padding、字号与 rpx 换算，WebView / Skyline 双端同一套 API。
- 耗不耗：一次批量查询 = 一次逻辑层↔渲染层往返（毫秒级），只在这几种时机跑：挂载后、`items`/`size`/模式变化、`onWindowResize`。**点段切换用已有快照，零查询**。
- 代价（已接受）：① 首帧量不到之前滑块先不画，避免闪到错位置；② 图标字体 / 图片晚到会让段宽变，量到后再校正一次（可能有一次可见微跳）；③ 等分模式完全不测，行为与现在一致。
