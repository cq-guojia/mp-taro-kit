## Background

2026-11-12 用户在图标分包讨论中提出：单色图标靠 `currentColor` 自动跟随明暗就够了；彩色图标颜色固化在 CPAL 调色板里改不了，需要「深色用 A 图标、浅色用 B 图标」，并希望调用方不用管。

前置实测与结论：

- `content: var(--mptk-i-x, "\e61c")` 在真机 Skyline 下生效，变量能把字形换掉（demo「图标 → 换字形能力验证」C 格由 home 变 logo）。
- `theme-auto` 是纯 CSS 媒体查询（`src/design/theme-auto.scss:9`），JS 读不到当前生效的是哪一套 → 运行时「自动选版」不可行。
- 因此走 CSS 变量 + 覆盖关系：有定义用变体、没定义回落默认，不写任何查找逻辑、不引入运行时主题状态。

2026-11-12 后续讨论把范围从「图标变体」扩到「整套样式 + 运行时热切换」：用户要求消费端在项目入口一处配置明 / 暗 / 自动，且运行时可在开关里随时切换；保存偏好暂不进库。这推翻了上面「不引入运行时主题状态」的前提，原文保留以便追溯。

「三选一」= 现行对外主题契约：`package.json:54-57` 的四个样式出口（`styles/tokens` 旧出口 + `theme-light` / `theme-dark` / `theme-auto`），宿主在 app 入口引一行、编译期定死；`docs/api/exports.md:87-101` 写明不需要 JS / `faces` 注入 / 根容器标记，`tests/ui.test.mjs:51-76` 断言守卫。本轮待拍板的是「再加一条路（并存运行时热切换出口）」，不是替换三选一。

## Conclusion

机制与工具链已落地，产物零变化（当前所有包都没有 `-dark` 图标）：

- `scripts/lib/icons-parse.mjs`：`parseIcons` 一个纯函数，不联网不落盘，返回 `icons` / `variants` / `paired` / `colored`。
- `scripts/icons.mjs`：`iconMap` = 主轴 + 变体；`iconNames` 只列主轴；`iconPaired` 列有暗色版的主轴名。
- 形态：一个包永远一个 `style/index.scss`，`logo` 与 `logo-dark` 两个类并存，用哪个由调用处按位置决定。
- 否决过的两条路线：`content: var()` 依赖 `page` 变量被后代 `:before` 继承（Skyline 未验，失败则变体图标整体消失）；`dark.scss` 覆盖是全页级的，做不到「明亮界面里的深色区块单独用暗色 logo」，而这正是真实场景。
- `tests/icons.test.mjs`：6 项断言全过（主轴/变体拆分、孤立 `-dark` 不变体、占位过滤、混合场景 `paired` 只含有变体的）。

未完成：真机验证暗色字形切换（缺真实 `-dark` 图标）；`prefers-color-scheme` 在 Skyline 下未验证，`auto.scss` 的正确性依赖它。

本轮定性：方案不是最优，存在 P0 / P1 / P2 坑，「没有坑就落码」的条件未成立 ⇒ 未更新任何文档、未改码、未跑 `pnpm test` / `pnpm run build`、未做真机验证。已收口的方向保留用户接受的「`app.tsx` 配置一次 + 模板 / Base + 不加 `height:100%` 包裹层」，换掉底层机制：三选一三条出口与 `tokens.css` 一字不动，新增并存的运行时主题出口；颜色值真源仍只在 `_tokens.scss`；主题状态进 `runtime` 复用单例；图标回调用处选择；`icons` 不挂 build。

影响结论：并存对已接入宿主的「一行 import」零影响；维护面集中在新增出口的 `build` / `check` / `test` / 文档同步，不产生第二份颜色真源；运行时开销为一次样式重算 + 一个 `onThemeChange` 监听 + 一次 `setBackgroundColor`。实测三份主题 CSS 为 `1752` / `1782` / `2299` B，`tokens.css` 是 `1752` B 的兼容副本；消费端只引自己那一份，新增第四份对单个宿主约 `+0.6 KB`，且不进老项目。

转场白闪的根因与根治（用户 Skyline 实测后本轮完成）：

- 现象：暗色下点首页菜单进子页，中间有一帧白色闪过，随后正常。
- 根因（原来写错的地方）：`src/design/_tokens.scss` 的 `base` mixin 把主题相关的 `background-color: var(--mptk-surface-base)` 混进了「页面基线」，四条主题出口共用它；编译期三选一把明暗值也放在 `page` 上所以无事，`theme-runtime.scss` 把暗色值挪到后代 `.mptk-dark` 后，`page` 就恒取明色值。后代 class 结构上改不了祖先，React 挂载前必然露白。改颜色值或铺遮盖都消不掉，属职责错配。
- 根治：① `base` 只留布局基线与非颜色变量，页面底色独立成 `surface` mixin，由出口决定是否 include；三条编译期出口 include，运行时出口不 include。② `demo/src/app.scss` 的 `page` 同步去掉底色声明。③ 页面底色交给微信官方窗口主题配置：`app.json` 开 `darkmode` + `themeLocation`，`window` 的 `backgroundColor` / `backgroundColorTop` / `backgroundColorBottom` / `backgroundTextStyle` / 导航两项全部用 `@变量`；`demo/src/theme.json` 定义明暗两档，由框架在页面创建前解析。④ `demo/src/app.tsx` 的窗口色改读同一份 `theme.json`，删掉硬编码 `WINDOW_BACKGROUND`。⑤ `PageShell` 铺内容区底色保留（Skyline 安全区既有要求），但文档写明它不是首帧解法。
- 踩坑：`theme.json` 初放 `demo/` 根，Taro 按 `sourceRoot` 去 `demo/src/theme.json` 读，编译报 `ENOENT`；移到 `src/` 后框架自动复制进产物根，无需 `copy.patterns`。回归断言初按字面比色值，`#fff` 与 `#ffffff` 误报，改为十六进制语义等价比较。
- 改前 / 改后：`demo/dist/app-origin.wxss:1` 原为 `page{box-sizing:border-box;height:100%;background-color:var(--mptk-surface-base);...--mptk-surface-base:#fff}`；现为 `page{box-sizing:border-box;height:100%;--mptk-radius-...`，无 `background-color`。`demo/dist/app.json` 原缺 `backgroundColor`，现有 `"backgroundColor":"@bgColor"` 与 `"themeLocation":"theme.json"`，`demo/dist/theme.json` 存在。
- 验证：`pnpm run build` 195 产物、`pnpm test` 56/56、`pnpm run guard`、demo `build:weapp`、docwriter `check` 9 篇、codelint 六层全过。
- 未完成：Skyline / WebView 双端实机确认首帧、`-dark` 真实字形切换；强制明 / 暗覆盖系统时的首帧色是微信平台边界，实测后记录。
