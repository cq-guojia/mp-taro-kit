关键判断：Vant / antd-mobile 架构一致——逻辑关闭只翻布尔，底层播退场，底层给完成点，完成后清理；Promise 在用户点击那一刻结算。但它们的完成点是 `transitionend`（Vue `Transition.onAfterLeave` / antd `afterClose`），微信小程序该事件非冒泡、关键帧仅 WebView，不能直接照搬。本库用自己已有且被测试锁死的 `usePresence` duration 计时（`MOTION_DURATION=300`，与 CSS token 同源，`tests/layout.test.mjs:880-888` 断言相等）作为完成点：借鉴架构，不照搬机制。

候选方案评估：
- 选 a（底层 `afterClose` 回调 + 宿主只记录 closing id）：完成点回到真正拥有动画的 `usePresence`，无第二套计时；不动 `overlay-stack` 公共语义；保留 pageKey/owner 体系；公开 API 只加可选回调。
- 不选 b（改 `overlay-stack` 加 closing 状态）：仍需要“动画完成”信号，等于在 a 之外再加一层 runtime 状态机；破坏 `dismiss` 立即移除的公共语义与 `tests/runtime.test.mjs:70-87`、`tests/ui.test.mjs:188-190` 的断言；违反 `overlay-stack.ts:1`“栈只存 payload”的边界。
- 不选 c（宿主本地缓存 exiting 载荷 + setTimeout）：与 `usePresence` 形成第二套计时，载荷快照可能过期，多页卸载双结算；即当前被否的补丁。

方案复盘后新增的两条**必须修正项**（原表述有漏洞，会导致实现走偏）：
1. `closingIds` 必须用 `useState` 且每次换新引用，不能用 `useRef<Set>`。理由：`DialogHost.tsx:135` 的 `open` 是渲染期从状态派生的，ref 变更不触发重渲染，则 `open` 永远不变 false，退场不会启动。这是方案陈述的漏洞，不是可选优化。
2. 退场的 300ms 内节点仍在且可点（`Popup.tsx:127-129` 保持 mounted，`DialogHost.tsx:157` 的 `onClose` 仍挂着）。新版 `dismiss` 入口必须先判 `closingIds.has(id)` 直接 return；`afterClose` 里的 `finish(id)` 也要幂等，防止二次 resolve / 重复出栈。

已识别的健壮性风险与对策（待落码时逐条验证）：
- `onConfirm` 异步期间 `busyRef` 早退（`DialogHost.tsx:84-85,92`）会挡住 cancel，这是既有行为，本任务不顺手改。
- owner 必须保留到 `afterClose`，否则 `DialogHost.tsx:39-42` 会让别的页宿主抢到 closing 条目。
- Promise 必须在逻辑关闭时立即 resolve，不能延迟一个动画周期（`commands.ts:220-234`、`docs/api/exports.md:65-67`）。
- 宿主卸载（`DialogHost.tsx:58-74`）与 `resetUIForTests`（`commands.ts:236-249`）要覆盖 closing 条目；迟到 `afterClose` 遇到无效 id 返回 `undefined`，`finish` 必须幂等。
- `duration<=0` 时 `usePresence` 立即卸载，也要触发一次 `afterClose`。
- `animateOnMount` 首帧的 `initialOpen=false`（`presence.ts:19-20`、`Popup.tsx:127`）不能误触发完成回调。
- `ImagePopupProps` 是独立接口，不随 `ContentPopupProps` 自动获得新 prop；本任务只改命令弹窗链路，不扩散到 Drawer / Dropdown / ImagePopup，除非测试暴露需要。

### 两路专家复核结论（2026-11-26，前端状态机专家 + 架构师）

用户指出“风险不只是 close，所有开启/按钮 loading 起止都要合理方案”，据此召集复核。两位一致确认方案方向正确（与 Vant / antd-mobile 的“逻辑关闭翻布尔 → 底层播退场 → 完成点清理”同构），但**只加 afterClose 不够**：DialogHost 已经有三个同属一个状态机的现存 bug，退场改造正好压在上面。

三个现存 bug（证据）：
1. **lockExceptions 被逻辑层吞掉**：confirm 默认 `lockExceptions=['cancel']`（`commands.ts:212`），`actionsOf` 把 key 映射成 lockKey（`DialogHost.tsx:123-125`），Button 放行（`Button.tsx:114-115,124-125`、`popup-lock.ts:20-27`），但 `runAction:92` 与 `dismiss:85` 的无条件 `busyRef.has(id) return` 把它吞掉——按钮看着能点、点了没反应。现有测试只断言渲染层例外（`render.test.mjs:1218-1239`），没覆盖点击后的状态机。
2. **setBusy(false) 早于 dismiss**：`DialogHost.tsx:107-108`。释放 Popup 的 `blocked`（`Popup.tsx:132-137`）与 CSS `pointer-events:none`（`style/index.scss:78-85`）；`actionsOf:116-126` 没透传 `loading`，Button 的圈来自 `onClick` 返回 Promise 的自动 loading（`Button.tsx:124-138`），会在 dismiss 后一个 microtask 退出，`loadingText` 回退（`:144`）。退场期 center 档面板仍停在屏幕中间（`style/index.scss:151-157`）且面板没有关闭态 pointer-events，按钮仍可命中 → 二次执行 `onConfirm`（当前因条目已删不会二次 resolve，但新方案保留载荷后会）。
3. **exiting effect 自毁 timer**：`visible` 每次 render 是新数组（`DialogHost.tsx:42`），effect 依赖 `[visible]`（`:55`），`setExiting` 自己触发 re-render → cleanup `clearTimeout` → 新 effect `gone.length===0` 直接 return，timer 不再建。A 退场后可能永久留在 exiting；关 A 立刻开 B 时 A 的 timer 被清掉且无人清 A。

新方案必须补的保护：
- `settledIds`：Promise 一次结算；`closingIds` 用 useState 换引用（延后 dismiss 后唯一的重渲染触发器，`use-store.ts:9-15`、`DialogHost.tsx:135`）。
- `actionSeq` 代际：取消/卸载/reset/重开后旧 task 的 success/fail 全部忽略；异步回调校验 `owner === token && !settled && !closing && seq 匹配`。
- `mountedRef`：卸载后不 setState；`finish` 幂等，容忍 `overlays.dismiss` 返回 `undefined`（`overlay-stack.ts:37`）。
- owner 保留到 afterClose；若逻辑关闭就清 owner，认领循环（`:39-41`）会给 closing 条目重新分配、出现“复活”。
- 关闭期强制锁死并忽略 lockExceptions，否则退场期还能点。
- loading 显式透传：closing 期保持 `loading=true` 且锁住，不让 loadingText 在动画里回退。

正确顺序：`mark settled + closing → resolve 一次 → open=false（保留 busy/lock） → afterClose → setBusy(false) + overlays.dismiss + owner.delete`。失败路径 `false/reject` 只在仍 open 且未 closing 时 `setBusy(false)`，不 resolve、不关窗。

架构师裁定：
- 状态归属可接受，前提是“dialogOwners 是唯一所有权真源，closingIds 只是重渲染提示”；卸载时全局清理仍执行（`:58-72`），不留残留。
- `resetUIForTests`（`commands.ts:236-249`）触不到局部 state，但 id 单调自增不复用、静态渲染不跨调用，无正确性 bug；老旧 closingIds 只是无害内存残留，`finish` 幂等即可。
- 多页场景 timer 会走（Taro 保留 A 树、`presence.ts:33` 的 setTimeout 在 A 的 effect 里），B 页被 pageKey + owner 双重挡住。
- 命名选 `afterClose` 不与现有 `onClose` / `resolve` 冲突（源码无 `afterClose`/`closed` 符号），但要写进文档属性表。
- 不推荐“DialogHost 内私有 usePresence wrapper”替代方案：会跑两个并行 300ms 时钟，完成信号来自观察者而非真正卸载节点的 hook，单一真源更弱。

不属本任务范围：自定义 action 成功统一 `resolve(key === 'confirm')` 的现有语义；通用 Button 的 onFailed 体验；React 并发渲染下 owner 认领迁到 commit-phase 的整体改造。

### 最终架构方案（2026-11-26 两路专家再讨论，用户点头执行）

用户进一步要求：“要足够健壮，能适配以后所有类似情况的解决。看还有哪些地方是为这个定制的？该抽象的要抽象到有可能的情况，最外层要做以后东西的适配。”重申后专家推翻了“只在 usePresence 加回调 + DialogHost 自管状态”的收缩版——那仍是以弹窗为中心的补丁，Toast/Loading/Login 未来要各写一遍。

全仓同类位置（证明不是弹窗专属）：`showToast/hideToast`（`commands.ts:51-76`、`notify.ts:40-45`）、`showLoading/hideLoading`（`loading-slot.ts:23-39`、`LoadingHost.tsx:21` 直接 return null）、`LoginDialog`（`login-dialog.ts:35-46`、`LoginDialogHost.tsx:19-20`）、FAB 条件渲染（`KitPage.tsx:127-133` 从 items 直接删）、ImagePopup `slides.length===0` 直接 return null（`ImagePopup.tsx:247`）。排除项：Switch/Segmented thumb、Button loading、Loader/Spinner 循环动画——都是常驻节点的状态动画，没有“逻辑关闭→物理卸载”链路。

最终三层架构：
- 第一层（视觉原语）：`usePresence` 加 `onExited`，完成点复用 duration；`animateOnMount` 通用化为 `initialOpen`。所有 presence 底座统一透传。
- 第二层（通用生命周期）：`overlay-stack` 条目加 `phase` + `markExiting/finishExiting`（`dismiss` 原语义不变）；ui 层 `createOverlayLifecycle<T>` / `useOverlayLifecycle<T>` 提供 `open/close/finish/clear/isCurrent/claim/release`，统管 settled 幂等、seq 代际、scopeKey/owner、mountedRef、卸载兜底。
- 第三层（业务专属）：DialogHost 只留按钮 / busy/lock / actionSeq / Promise 结算；Toast/Loading/Login 业务语义各自保留；未来新浮层只做 open/finish 适配 + 接 onExited。

最外层：`HostKind`/`hosts` 改成可扩展 key；`createKitApp/KitPage` 不新增平行注册表（现有 `kitHosts` 够用，`docs/api/app.md:19-24` 规定 Host 必须在页面树）。

明确不做：runtime 不持 timer / transitionend / CSS duration / React 回调；`dismiss()` 不改语义；不让 Host 再跑一套 300ms；不在 app 层加第二套注册表。

两条不变量（未来适配靠它们，不靠枚举补丁）：① 有退场动画必须走 `usePresence` 并在物理节点给 `onExited`；② 外部状态源关闭时不许直接卸载，只能 `lifecycle.close → onExited → lifecycle.finish`。
